Reproduce it with `node dev/measure.mjs --ref 3fed971` (commit `3fed971` is the last one before the redesign; its product code is exactly 0.6.0, and there is no `v0.6.0` tag). Synthetic folders only.

## 1. Short answer

- ❌ **0.6.0 organizes nothing, and the scores show it.** No map anywhere, 0% of notes findable from a map, loose files at the top unchanged (30 → 30 in the everything-folder), no duplicate resolved, no new item filed.
- ⚠️ **It spots some problems, mostly with Git.** In the everything-folder it surfaces 3 of 8 planted problems with Git and 1 of 8 without. It misses broken links in loose notes, empty notes and duplicates.
- ✅ **Safety is perfect**, because 0.6.0 only adds files: nothing lost, code untouched, links intact, undo restores the exact original. The redesign must keep this at 100% while it starts moving files.

## 3. How to read it

| Folder | What it is |
|---|---|
| **spaghetti** | An everything-folder: 12 photos and screenshots, 6 PDFs, 14 loose notes on several topics (with an exact copy and a near copy), `old/`, `New Folder/`, `stuff/`, a small website whose code uses two files at the top by name, scattered checkboxes, a broken link, notes nothing links to, two old notes |
| **spaghetti-nogit** | The same folder without Git: old notes are dated by their file date only |
| **code-sprawl** | A program with tests and a model file it loads, 6 screenshots at the top, two document folders (one named in the rules), a loose report, three results folders, an "old debug files" folder |
| **flat-notes** | A second brain kept flat: 19 notes on three topics with `[[wiki links]]`, attachments, a near copy, old notes |
| **tidy** | The control: already organized, with its own README navigation. A good result here is "almost nothing to change" |

- **Find** counts notes reachable within two links from `MAP.md` (map → area index → note), leaving out front doors (README, rule files) and archived notes. The tidy folder's own README navigation reaches its notes, but the score counts only from `MAP.md`, by design.
- **Loose at the top** leaves out front doors, manifests, lock and config files, and files the code uses by name (they must stay).
- **Nothing rots** counts a planted problem only when a line of the check or briefing output names the file **and** says what kind of problem it is. A file name inside a list of something else does not count.
- **Open work in one list** is the largest share of planted open items that any single page holds.
- **New input** drops the planted items where a person would (into `inbox/` when there is one, else at the top), starts a session, and checks that each item ended up beside its family in a folder, or in `inbox/` when it has none.
- **Safety** compares before and after: a file is lost when it is neither where it was nor anywhere else with the same content (only links may differ). Undo is checked on a fresh copy: set up, undo everything, compare.

## 4. Proposed targets for the release

These follow from the design's outcomes; the maintainer can change them.

| Outcome | Target on the test folders |
|---|---|
| Safety (all four rows) | ✅ on every folder, every run. A slice that breaks it does not ship |
| Orient | `MAP.md` covers every top-level item; pointer in the rulebook; briefing on |
| Find | 90% or more of notes within two links of `MAP.md` (100% on tidy) |
| Loose at the top | spaghetti 3 or fewer, code-sprawl 1 or fewer, each with a stated reason; tidy stays 0 with no move proposed |
| One home | Every exact copy resolved by the one-click plan; near copies **surfaced** for the judgement pass (merging needs a yes, so it is not counted as automatic) |
| New input | All planted items land right once standing rules exist (the item without a family lands in `inbox/`) |
| Nothing rots | All planted problems surfaced, with and without Git |
| Open work | All planted open items in one list |
| Low ceremony | Live run: at most 3 questions, one yes for the plan |

## 5. The measurement tools

| File | What it does |
|---|---|
| `dev/fixtures.mjs` | Builds each test folder the same way every run (same bytes, same Git dates) and records what was planted |
| `dev/score.mjs` | Scores a folder with its own file walk and link reader (Markdown links, images, reference links, angle brackets, `%20`, `[[wiki links]]` with aliases, folder links; code blocks skipped), so repo-fit's own code cannot hide its bugs |
| `dev/measure.mjs` | Runs a repo-fit version on every folder in a temporary place with a fake home, the way the skill would after a yes to everything offered, then scores, drops new input, starts a session, and checks undo on a fresh copy |
| `test/measure.test.mjs` | 7 tests that the folders are stable and the scorer counts what it should |

While building them, the first run exposed two weaknesses in the scorer, both fixed with tests: a file **edited in place** was reported as lost, and a duplicate counted as "surfaced" when its name only appeared in a list of unlinked notes.

## 6. Limits

- The folders are small and synthetic. They model real messes but are not real data; pilots on copies of real folders come at release, with the maintainer's approval for the exact folders.
- "Surfaced" matches wording in the output; a future check that says "copy" or "duplicate" in other words may need the word list updated.
- 0.6.0 is driven the way its skill would after a yes to everything it recommends (`audit` → recommended `apply` → `hooks`). A real person might choose fewer pieces.
- Measured on this Mac only (macOS, Node 23.7). Not run on Linux or Windows yet.
